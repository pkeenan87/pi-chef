# AGENTS.md

Pi extension that plans, builds and reviews coding work with the right model for each job (/plan, /build, /review), with role-based routing and cost tracking. See README.md for user-facing behavior, and `docs/` for commands (`commands.md`), configuration (`configuration.md`: every setting), providers (`providers.md`), install and layout (`install.md`), and the Pi API surface (`COMPATIBILITY.md`). This file is for agents working on this repo. When a change alters user-facing behavior, update the doc that describes it; a new command or argument goes in `docs/commands.md`, a new config key in the settings reference of `docs/configuration.md`.

## Commands

```bash
npm test            # vitest, no network
npm run typecheck   # src and tests
```

Both must be green before you call a change done. There is no lint script.

## Layout

- `src/extension.ts`: Pi entry point. Registers commands, the session hooks (`session_start` model pin, `session_before_compact`, `input` budget gate, `message_end` ledgering), providers, and web tools. Keeps one `Workflow` per cwd. Holds the `/build` session driver (`buildHost`), the only code that opens Pi sessions for tickets.
- `src/commands.ts`: the command table (name, description, `run`; `drive` for `/build`, which the host runs with a session driver).
- `src/orchestrator/`: `service.ts` is the `Workflow` facade. Each command lives in its own module (`planning`, `plans` (/plans list, switch, close), `tasks` (names, listing, `activeTask`, closing), `interview` (the `/plan` interview and spec), `ticket-plan`/`tickets` (ticket validation, files, group mapping), `prompts`, `build` (`/build`: `startBuild`, `nextChunk`, `finishChunk`, and `runBuild`, the loop, pure over a `BuildDriver`), `review` (`/review`: findings dialog and fixes in the current session), `advisor`, `reports` (`/cost` and `/status`: the status tables go to `ctx.report`, the command returns the one-line state from `state-label.ts`; keep `/status` free of model calls and az), `compaction` (the cheap-tier compaction summary), `routing` (availability and route announcements), `status-foundry` (`/status foundry`)) as a function over `WorkflowContext` (`context.ts`). Phase rules are in `machine.ts`.
- `src/router/`: `classify.ts` (`classifyKeywords`, the deterministic security-keyword scan, and `plannerClassification`, the planner's `plan_spec` rating with the scan as a floor; no model classifies), `policy.ts` (tier choice, escalation; ticket tiers `ticketLow`/`ticketMedium`/`ticketHigh` and the `TICKET_LADDER` up to premium), `select.ts` (picks the model within a tier: `routing.selection` ordered (default, first usable in the tier's order, the reason names what it fell back past) or adaptive (cost per success with Thompson sampling)), `stats.ts`.
- `src/providers/`: `auth.ts` (account-login, az, vercel status), `clients.ts` (chat clients, usage parsing), `runtime.ts` (registers foundry, vercel, and local with Pi), `vercel.ts` (OIDC token via the Vercel CLI), `pi-chat.ts`, `usable.ts` (why a provider or candidate cannot be used: config, login, Pi registry).
- `src/cost/ledger.ts`: spend summaries and budget status. `src/cost/quota.ts`: subscription quota use per provider (ranking only). `src/config.ts`: YAML layering, validation, and pricing.
- `src/storage/store.ts`: task state, the event log, the ledger, metrics, and locks.
- `src/git/workspace.ts`: `GitWorkspace`, git over `execFile` for the main checkout (branches, merge-base, working-tree diff, `commitAll`). Nothing in the repo pushes or talks to a forge.
- `src/review/`: checks and static review (`review.ts`), the advisory model pass of `/review` (`model-review.ts`), and the shared advisor client (`advisors.ts`: `consultAdvisors`, the pure `advisorsFor` rule). `src/orchestrator/ticket-review.ts` is the per-ticket review of `/build`; `Store.appendTicketLog` writes the append-only `metrics/tickets.jsonl`. `src/orchestrator/review-report.ts` builds the `/review` tables and the numbered items the findings dialog and Fix all share; `progress.ts` is the live progress line.
- `src/tools/`: `web_search` (Anthropic subscription, Haiku), `web_fetch` (local, public-only), and the plan tools `plan_questions` / `plan_spec` / `plan_tickets` (`plan-questions.ts`, `plan-flow.ts`, `plan-review.ts` (`presentForDecision`: the single inline path for the plan decision, `/show-plan` and `/review`: markdown in the transcript, then a `ui.select` of actions, no popup). `plan_tickets` never asks mid-turn: Pi holds `sendMessage` until the turn ends, and `ui.notify` is dim plain text. It commits the draft with `presentPlan` set, and the `agent_settled` handler in `extension.ts` runs `present-plan.ts` (`presentPendingPlan`) on its live ctx once Pi is idle: post the plan, pick, approve, request changes (`requestPlanChanges`), or edit tickets. An aborted turn keeps the flag; `readonly-bash.ts` is the planning bash allowlist).
- `src/sandbox.ts`: one command walker (`commandsIn`: wrappers such as `timeout`/`env -S` stripped, `sh -c`, `eval` and `find -exec` followed, inline `git -c alias.*` expanded) behind the deny rules (`assertCommandSafe`) and the `/build` bash block (`buildBashBlock`). `src/redact.ts`: secret redaction.

## Rules that are not obvious from the code

- **Account providers (OpenAI, Anthropic, xAI) use Pi account login by default.** A key stored in Pi (`/login` with a key) is used only when the user config sets `providers.<name>.apiKeyFallback: true`; a project config cannot set it (`restrictProject`). While a provider is on a key, prices come from `billing: api-key` rows (`setBillingResolver`, fed by `FileAuthProbe.billing`); with no such row the cost is unknown, never the subscription's $0. Never read `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, or `XAI_API_KEY`. Do not name a config field so it ends in a secret word (`apiKey`, `token`): `containsSecret` rejects it.
- **Foundry fallbacks are tier entries, and `api` is per deployment.** Each OpenAI or xAI entry in `DEFAULT_TIERS` and the sample config is followed by a Foundry deployment that is simply unavailable without an endpoint and `az login`. `providers.foundry.api` is the provider default; a Foundry `TierCandidate.api` overrides it per model in `registerChatProviders` (first tier wins, `foundryApiConflicts` warns). All chat goes through Pi's registry, so the registered api is the one used. Cross-vendor advisor choice uses `vendorOf` (model name), not the provider. Foundry is per token: pricing rows, no `quota.models` rows.
- **No secrets in config.** `assertNoSecrets` enforces this. Tokens (az, vercel, oauth) live in memory only. Never log them or write them to state, the ledger, or prompts.
- **Policy is deterministic; models only advise.** Plan approval stays required. Merge stays manual (`approvals.merge`); nothing pushes, opens a PR, or merges. A project config can never loosen the user's policy fields (`orgProviderAllowlist`, `proprietaryCode`, approvals, budgets).
- **A project config can only tighten `advisors`, `session` and `budgets`.** `layerConfigs` (`restrictAdvisors`, `restrictSession`): advisor switches can only go off; `maxDiffChars`, `maxOutputTokens`, `timeoutMs`, `maxPlanConsults` take the lower of user and project (DEFAULTS when the user sets none); `adHocMinLines` the higher. `session.model` and `compactionTier` are user-only; a project may set `pin: false`. `routing.reviewTier` and `workspaceDir` are user-only, a project's `routing.requirePremiumReviewFor` adds to the user's list, and `circuitBreakerFailures` takes the lower value (`restrictRouting`). A project pricing row cheaper than a user row for the same provider/model/billing is ignored. Budget limits are compared with DEFAULTS when the user sets none. Ignored values warn in `config.warnings`.
- **Advisors obey the hard exclusions of `selectCandidate`.** `availableAdvisors` calls `hardExclusion` (`router/select.ts`: allowlist, proprietary code, open circuit, budget) and returns a note per excluded advisor; callers put the notes in `advisorsSkipped`. Do not copy those rules.
- **plan_consult is keyed on content.** `consultHash` (spec plus canonical tickets) is stored on the consult; `plan_tickets` refuses a different hash unless `reconsultWaived: true` with a resolution. At most `advisors.maxPlanConsults` consults per draft version; one in-flight consult per task.
- **Resume keeps the tier.** `prepare` (build.ts) takes the ticket's tier from its latest attempt whatever the status: failed escalates one tier, aborted or in-progress resumes on it. Review rounds are counted per tier (`item.tier`), not per attempt number. A hand-fixed ticket (`nextChunk`) goes through `reviewTicket` with no implementer before its commit, records an unattributed `hand fix` attemptLog entry, and bumps no model metric. `reviewTicket` never throws: any exception is an `unavailable` review.
- **Credential and location fields are user-config-only.** `baseUrl`, `endpoint`, `endpointEnv`, `apiKeyEnv`, `audience`, `projectDir`, `envFile`, and `resourceGroup` from a project config are ignored with a warning (`config.warnings`, shown by `/status`), unless the user does not define that provider and the value is the built-in default. Remote endpoints must be https; only `local.baseUrl` may be http, and only for loopback.
- **Routing availability and the /build preflight use the same checks.** `availability` (`orchestrator/routing.ts`) probes every provider, configured or not: an account provider needs a Pi login even when the config never names it, and foundry/vercel/local need their block (a provider left out of the map used to count as available, which routed to a provider Pi had no login for). When a Pi model registry is bound (`Workflow.bind({ registry })`), every candidate must also pass `registryProblem` (`providers/usable.ts`: `modelRegistry.find(provider, piModelId)` and `hasConfiguredAuth`), the test the preflight in `buildHost().fresh` runs. Skip and stop reasons come from `usable.ts` (`configProblem`, `authProblem`, `registryProblem`) and are used verbatim in route events, `/status`, and stop messages; change them in one place. A new route path passes `candidateCheck(ctx)` to `selectCandidate`.
- **Config errors are always surfaced at session start.** Keep the try/catch so a bad file cannot crash the session, but never swallow the error: `session_start` shows it through `ctx.ui.notify(..., "warning")`, redacted, naming the file and key (`problemNotice` in `extension.ts`); errors found at extension load are deferred to the next session start. Loading real files is lenient only for sections that cannot loosen policy (an invalid `tiers.<name>`, `session`, or `quota` section drops just that section with a warning). Secrets, `approvals.merge`, `restrictProject`, providers, budgets, routing, and unreadable YAML reject the whole file (`ConfigFileError`). Do not widen the lenient set.
- **Foundry `deployments` maps a model to a deployment.** The tier `model` stays the key for routing, metrics, and pricing. Pi is registered and called with `foundryDeployment(config, model)` (`piModelId`), and labels show `modelLabel` (`foundry/<model> → <deployment>`). `applyDeploymentPricing` makes the deployment's pricing row win and prices both names alike. `/status foundry` is the only place `az` runs for diagnostics, and only on request. There is no `models:` default any more: `tierCandidates` is the config's tiers, then `DEFAULT_TIERS`.
- **Unknown cost is never treated as zero.** Record `actualUsd: null` and let the budget treat it as spend: an estimate from tokens and the dearest price, else the flat `budgets.unknownCallUsd` (default 0.05; a project can only raise it, so the higher value wins in `layerConfigs`). The estimate lives in `summarize` only, never in a ledger row, and an unknown row no longer makes the status soft by itself. Do money math in integer micro-USD (`toMicroUsd` and `fromMicroUsd`).
- **Spawn processes with `execFile` and argv arrays, never a shell.** Put `--` before user-derived refs. Every check and setup command must pass `assertCommandSafe` (the deny rules).
- **Writes to `.pi-workflows/` go through `atomicWrite`, `withLock`, or append-only files.** Never truncate `events.jsonl` or the ledger.
- **Never use a ctx or `pi` captured before a session replacement.** `/build` opens a new session per ticket (`newSession`); Pi then invalidates the old ctx and pi, and any use throws. Post-replacement work goes through the ctx passed to `withSession` (`replacementCtx` and `live` in `extension.ts`), and the workflow is re-resolved from it (`workflowFor`) on every call.
- **Never throw inside `withSession`.** Pi rethrows an error from the callback out of `newSession` and the app dies with "Failed to create session". The `/build` driver (`buildHost` in `extension.ts`) catches everything in there, stashes it, and returns normally; after `newSession` resolves it returns `{ stopped }`, which `runBuild` turns into a failed `CommandResult`. Before `newSession` it preflights the routed model (`modelRegistry.find` and `hasConfiguredAuth`) and stops cleanly without opening a session. If the stop comes before the ticket's first turn (`sent` is false), `runBuild` calls `unstartChunk`: the run goes back to what it was (no attempt, no pinned tier, no `currentTicket`, no metric). `prepare` also treats an in-progress run with no turn, usage or time as not started.
- **No empty model ids.** `tierCandidates` never returns a candidate with an empty `model` (a legacy `models` entry with no `providers.<name>.model` is dropped) and falls to the built-in `DEFAULT_TIERS`, the sample config's lists without prices; `selectCandidate` also refuses an empty id (`no model id`). A tier with nothing usable moves up the ladder; with nothing left the route is blocked with "No model configured for tier <tier>; add tiers.<tier> to your config." Models of a tier without a `pricing` row add one config warning.
- **`/build` drives Pi sessions only from `extension.ts`.** `newSession`, `sendUserMessage`, and `waitForIdle` are called from the command ctx or the replacement ctx, never from lifecycle handlers. `build.ts` stays pure over `BuildDriver`. The chunk model is set through the `RESTORE_MODEL` slot, which `session_start` reads (`restoreModel`) before `withSession` runs; the driver waits on `RESTORE_DONE` and refuses to start a ticket on the wrong model. Tickets run in the main session, so there is no child process, worktree, or pool.
- **The active task resolves from the git branch, then from `active-task.json`.** `activeTask(ctx)` (`orchestrator/tasks.ts`) is used by commands and reacts to branch *changes*: `active-task.json` stores `{taskId, seenBranch}`; only when the checked-out branch differs from `seenBranch` is it looked up, and if it is an open (not COMPLETE) task's `build.branch` that task becomes active; otherwise the stored task stays (default branch, a branch no task owns, detached HEAD, git failure, an old file with no `seenBranch`). `setActive` keeps the recorded `seenBranch` unless given one (`/plans <name>` and `/build`'s switch pass the branch current then). One git call per command. Hot paths (`observeUsage`, budgets, `message_end` ledgering, the plan tools mid-turn) use the stored task via `active`/`requireActive` and must never call git. `/plan` never replans another task: it makes a new one, closes a finished active one, and parks an unfinished one untouched (`retireCurrent` in `planning.ts`). A task's `name` (`slugName`, unique with `-2`) is for people and the default branch (`<branchPrefix>/<name>`); the id stays the directory name, and a task without a name shows one derived from its request (`displayName`). Closing (`/plans close`, `closeTask`) moves a task to COMPLETE with `closedAt`/`closedReason`; it never touches git, branches or files, and never calls the branch resolver.
- **Phase changes go through `transition`, which checks `machine.ts`.** Commands return results through `guard` and do not throw to Pi. Any task can move to COMPLETE (closing). A command result is plain text: markdown escapes (`\|`) belong only inside table cells (`cell`), never in `taskState(...).line` or a result.
- **Ticket `checks` are command lines, never prose, and run without a shell.** `validateTickets` rejects a check the deny rules would refuse, one with shell syntax (`&&`, `|`, quotes, `$`, globs, redirects), and one whose first word is not a command on `PATH` (`checkLineProblem`), and `TICKET_RULES` tells the planner so. Checks get a 30-minute timeout and 64 MB of output (`exec.ts`). Checks and setup run any other command. A check that still cannot run (`ran: false`) stops the ticket as failed without escalation and without a metric strike: a pricier model cannot fix a plan. Only model-attributable outcomes feed `bumpMetric` and escalate: an unrunnable check or failed setup resumes on the same tier, and a ticket still failing on the top tier it can reach (premium, `routing.maxTier`, or a tier with no different models above it: `escalateImplementation` returns it unchanged) stops with `MAX_ESCALATIONS`.
- **Ticket spend is ledgered from the main session, priced from config rows like every other call.** `observeUsage` (`budget.ts`) records each assistant message with ` · ticket <id>` in the reason while `state.build.currentTicket` is set, and `record` tags any other call made then (compaction, `web_search`, batch summaries) the same way; `finishChunk` sums those entries (`ticketSpend`). Unknown cost stays `null` and makes the ticket cost unknown, never zero. Failures before any model request are a known $0 (`knownZero`), never `emptyUsage()`.
- **A new plan version resets run state through `forNewPlan`.** Attempts restart and only the runs of tickets whose text is unchanged are kept, so a revised ticket is built again.
- **One status line.** `refreshStatus` in `extension.ts` draws the `chef` footer from `Workflow.statusLine()` (`statusLine` in `state-label.ts`: task, state and next step, running ticket's model, task spend), after every command, planning stage, route, and session start. It uses the stored active task, never git. Do not add other `setStatus` keys.
- **Recovery and commit scope.** `commitAll` unstages its excluded paths after `add`, so a pre-staged `.pi-workflows` file never lands in a commit; `workingDiff` takes the same exclusions. `prepare` stores `attemptStart` (time and HEAD) on the run; `nextChunk` records an in-progress ticket as done when a commit with its subject (`commitSubject`) exists after that HEAD, so a crash between commit and save does not rebuild it. A task is finished (`isFinished`) only when its tickets are done and its review passed; a new `/plan` parks an unreviewed one. A commit without checks or review sets `unverified` on the run.
- **The progress line is bound to the live ctx.** `ProgressIndicator` (`orchestrator/progress.ts`, `ctx.indicator`) draws one `setWidget` line while /review runs and /build is between ticket turns. `extension.ts` passes `indicatorSink` (the live ctx's UI) on every `bind`; `attach` swaps it, so a replaced session's ctx is never drawn on. Always `stop()` in a `finally`; timers come from the injected `IndicatorTimer` (unref'd), and tests inject a fake indicator, never a real interval.
- **The chat trail is part of the product.** `ctx.progress` posts one-line events (`ui.notify` info) and `ctx.report` posts multi-line markdown blocks (`sendMessage` with customType `chef-report`); both stay in the transcript. `/build` reports each ticket (model, time, cost, checks, commit) and ends with a table; `/review` reports every stage with elapsed time (`src/orchestrator/format.ts`); keep that when changing them. Timings come from `ctx.now()`, never `Date.now()`, so tests stay deterministic.
- **The branch-level model review advises; the per-ticket review in `/build` gates.** `/review`'s `passed` comes from the checks and the static findings only. `modelReview` findings are stored and shown for a person; do not fold them into `findings` or `passed`. Setup commands (`setup:`) run in the repo root before the checks. The static scan reads only the lines the diff adds, from the raw diff (a redacted diff would hide the secrets it looks for); the report stores it redacted. By the user's decision, the Opus review of each ticket in `/build` (`src/orchestrator/ticket-review.ts`, called from `finishChunk` after the checks and before the commit) does gate the commit and the escalation: a first fail sends findings back to the same session, a second fail fails the ticket at that tier. Advisors (`src/review/advisors.ts`) never gate on their own; only Opus's final verdict counts, and a review that cannot run is `unavailable` and the ticket is committed with a warning. A ticket whose review failed (`failedBy: "review"`) is never committed by the hand-fix path of `nextChunk`; it goes one tier up. `routing.maxEscalations` caps those steps from the ticket's difficulty tier.
- **The main session is a normal Pi model pinned by `session.model`; there is no virtual model or router.** `session_start` sets `session.model` through the live instance's `pi.setModel` when `session.pin` is on, the session is on another model, and no `/build` model is pending in the `RESTORE_MODEL` slot (that slot wins). `finish()` in `buildHost` restores `session.model` when pinning is on, else the model the user had. Compaction runs on `session.compactionTier` through `session_before_compact` (`compactWithCheapTier` in `extension.ts`, `summarizeForCompaction` in `orchestrator/compaction.ts`): it returns `undefined` on any failure or a hard budget so Pi compacts with the session model, and it never throws. The hard budget blocks prompts through the `input` hook (`gateInput`): non-command input that is not `source: "extension"` gets `{ action: "handled" }`; `/` commands and extension-sent input always continue.
- **Nothing classifies by model.** The request gets `classifyKeywords` when `/plan` starts. `plan_spec` carries `complexity`, `risk`, `securitySensitive` and `classificationReason`, and `savePlanSpec` turns them into `state.classification` (source `planner`) with `plannerClassification`. The keyword scan of the request and spec can only raise the security flag, never lower it (a test pins this). `Classification` has no confidence; its source is `keywords` or `planner`.
- **Advisors advise; the review model resolves.** Advisor answers never gate and never change `passed` or approval. `plan_consult` (spec, compact draft tickets, 2-3 questions; both advisors) runs once per plan version: the stored `planning.consult` is returned on a repeat, and a revision clears it. `plan_tickets` refuses without it (and without `advisorResolution`) only while `advisors.plan` is on and an advisor is available and not budget-skipped. `advisorsFor` and `/review`'s `reviewAdvisorsFor` give advisors from `advisors.fromDifficulty` (default `high`: high ticket both, everything else none; `medium` adds one from another vendor for medium tickets and for ad-hoc branches above `advisors.adHocMinLines`), then one resolve call by the review model accepts or rejects each finding; only accepted findings are numbered and sent by Fix all. Advisor packets never include the session transcript, only the spec, tickets or diff, findings and questions, redacted.
- **The `batch` tier is for standalone jobs** (no conversation), such as `cut-summary.ts`'s one-line summaries of files a diff clip cut. `cheap` is for in-session subtasks. A config without `batch` runs it on `cheap`. Batch calls are ledgered (`batch summary`), skipped on a soft budget, and never a reason for a review to fail.
- **Price every new model.** Add a row to `pricing` in `.pi-workflows/config.yaml`, or the selector ranks it last as `price_unknown`.
- **Quota shadow prices and the attempt overhead rank; they never bill.** `routing.attemptOverheadUsd` (added to every priced candidate's price before dividing by its success rate, so a $0 model's record still matters), `quota.models` weights, and the `quota.providers` caps (`src/cost/quota.ts`, `shadowCost`/`rankingCost` in `src/router/stats.ts`) only change scores. Never add any of them to `actualUsd`, `budgetStatus`, `budgetRemainingUsd`, the over-budget filter, or `expectedUsd`. Give a new subscription model a `quota.models` row as well as its $0 `pricing` row.
- **Commits are the user's.** `GitWorkspace` supplies the `pi-chef <pi-chef@localhost>` name or email only for the part git has no configured value for (config at any level, or `GIT_AUTHOR_*`/`GIT_COMMITTER_*`); it resolves this once per workspace. `commit.gpgsign=false` stays so a signing prompt cannot hang a commit.
- **Do not let a ticket publish.** While a ticket runs the `tool_call` hook blocks `git push` and branch switches (`buildBashBlock`), and `commitAll` runs with `core.hooksPath=/dev/null` and `--no-verify` so hooks a model wrote never run. The hook is defense in depth; no command of this extension pushes.
- **Who does what is config, not code.** `session.model` is the main session, `session.compactionTier` serves compaction summaries, `routing.reviewTier` serves the `/review` model pass, which falls back to `standard` candidates. `/build` routes a ticket by `difficulty` (`low`/`medium`/`high`, from `ticketDifficulty()`, which also maps old `suggestedTier`) to `ticketLow`/`ticketMedium`/`ticketHigh`, starts every ticket on its own difficulty tier (a security-sensitive plan does not raise it: the planner rates auth, secrets, untrusted-input and egress tickets high, `/build` still confirms first, and `/review` and the per-ticket review stay on Opus), and climbs `ticketLow`, `ticketMedium`, `ticketHigh`, `premium` on failure. The proven-tier shortcut does not apply to ticket tiers. A tier the config does not list uses the built-in list (`DEFAULT_TIERS`, the sample config's models); only if that has nothing usable do the ticket tiers fall back to cheap/standard/premium. Review outcomes use `reviewMetricType(taskType)`.
- **Local mode never routes a ticket to the cloud.** `/plan --local` (or `localMode.default`) sets `state.localMode` and `plan.localMode`. Every ticket of such a task runs on `tiers.local` (one model; `LOCAL_LADDER` has no step up), and a down server is `NO_CANDIDATE`, never a cloud fallback. There is no size flag: `localProfile(config)` reads the size from the model tag (`modelSizeB`) and the window from `contextWindow`. Under 14B or unknown: low only, 2 files; 14B and up: low or medium, 3 files; target half the window. `checkTickets` applies it (`localTicketProblems`: also numbered implementation steps, and a check when the config has none); the planner gets `LOCAL_PLAN_NOTE(profile)`, `TICKET_RULES(target, true)` and `LOCAL_TICKET_RULES(profile)`. The chunk prompt is `LOCAL_CHUNK_RULES` with `ticketPrompt({ local: true })` (no spec, clipped context). Compaction during a local ticket returns `undefined` so the transcript stays on the local model. Planning and the per-ticket review stay on the session and review models (the user's decision). An unpriced `local` model is a known $0 in `priceFor`. `tiers.*[].contextWindow` is what Pi is told for a model.
- **Tests use fakes for transports, clocks, rng, `az`, and `vercel`.** Never make a real network call. Put shared fixtures in `tests/helpers.ts`.

## Unverified against live services

The `/build` session loop has only been run against fakes. Unverified: `sendUserMessage` resolving when the run ends, the order of `waitForIdle` and `agent_settled`, calling `newSession` again from inside the replacement ctx's `withSession`, Esc while a command is awaiting, and `setModel` through the `session_start` slot (including that it finishes before `withSession` runs). Also unverified: that Pi uses the summary a `session_before_compact` handler returns (and counts its `usage`), that an `input` handler returning `{ action: "handled" }` stops the prompt before any model call while `/` commands still run, and `setModel` from `session_start` for `session.model` (set without awaiting, so a prompt typed at once may start on the old model). Also unverified: the `message_end` usage fields, the `modelRegistry.complete` call shape, `web_search` over oauth, and Vercel `!command` key resolution in Pi. When you change these, say so in the PR. Do not claim they work without a live check.
